## #36 — Email/password signup path is non-transactional — apply create_restaurant_for_user RPC (#35 follow-up)
**Outcome:** Fixed
**What was found:** Unlike Google OAuth signup (fixed in #35 via `/api/auth/create-restaurant`), the separate email/password route `app/api/auth/signup/route.ts` still did 5 sequential non-transactional PostgREST calls (`users` insert, `restaurants` insert, `seedDefaultRestaurantRoles`, `restaurant_users` insert, `restaurant_setup_status` insert) after `auth.admin.createUser`. A failure after the `restaurants` insert would leave an orphan restaurant row (the code only rolled back the auth user, not partial `public` schema rows) — exactly the bug class #35 fixed for OAuth, just not yet applied here. Confirmed this was still true on disk (`cloudflare-staging` branch, matches `origin/main`), not something already fixed by later work.
**What was done:** Rewrote `app/api/auth/signup/route.ts` to call the same `createRestaurantForUserAtomic()` helper (wrapping the `create_restaurant_for_user` SECURITY DEFINER RPC from #35's migration `20260709180000_create_restaurant_for_user.sql`) instead of the 5 manual inserts. Removed the now-unused `seedDefaultRestaurantRoles` import from this file (left the helper itself in place — it's still used by `scripts/verify-sign-in-methods-staging.ts`). The existing catch block's `auth.admin.deleteUser(authUserId)` rollback is now sufficient because the RPC is atomic: any failure inside it means zero `public` schema rows were written, so there's nothing else to roll back.
**Verification:** Added `scripts/verify-email-password-signup-staging.ts` (same pattern/convention as #35's staging verify script) and ran it for real against staging (`mdqjpxwczrhkxkbqatqa`, via `.env.test`). Real run created a genuine `auth.users` row, called `createRestaurantForUserAtomic`, and confirmed: `public.users` row created, `restaurant_users` links owner correctly, 6 `restaurant_roles` seeded, `restaurant_setup_status` row created, orphan-restaurant count unchanged (0 before/after). Then tested the failure path — a second `create_restaurant_for_user` call for the same user was rejected by the RPC's existing-restaurant guard (`P0001: Restaurant already exists for this account`) and confirmed no partial/orphan restaurant was left behind. All assertions passed; test data cleaned up after.

## #34 — Misleading 'signed up with Google' hint shown on any invalid-credentials error
**Outcome:** Fixed
**What was found:** `app/signin/signin-client.tsx` still unconditionally appended `GOOGLE_SIGNIN_HINT` to any Supabase "invalid login credentials" error, with no check on whether the account actually lacks a password credential — exactly as described, and not touched by the later Sign-in Methods feature work (that work added the ability to *add* a password credential from Settings, but never touched the sign-in error path).
**What was done:** Added migration `20260714120000_signin_google_hint_check.sql`: a `SECURITY DEFINER` SQL function `public.should_show_google_signin_hint(p_email text)` (service_role only) that returns true only for a confirmed Google-only account (has a `google` identity, no `email` identity, and no `has_password_credential` metadata fallback) — false for everything else, including nonexistent emails, so it isn't a broader account-existence oracle than the app already has. Added `app/api/auth/signin-hint/route.ts` (POST `{ email }` → `{ showGoogleHint }`) calling that RPC via the service-role server client, failing closed (`showGoogleHint: false`) on any error. Updated `signin-client.tsx` to call this endpoint after an invalid-credentials error and only append the hint when it returns true, instead of always appending it.

All 4 passed. Also directly exercised the actual Next.js route handler (`POST` from `app/api/auth/signin-hint/route.ts`) against staging credentials to confirm the API layer itself (not just the SQL function) works, then deleted the scratch harness.
