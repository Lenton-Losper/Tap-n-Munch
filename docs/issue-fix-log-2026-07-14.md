## #8 — Chore: sync-profile repair can reassign restaurant owner_id unexpectedly
**Outcome:** Fixed
**What was found:** `app/api/auth/sync-profile/route.ts`'s relink path unconditionally ran `UPDATE restaurants SET owner_id = <repaired auth id>` whenever an account was relinked by email, regardless of the relinked user's role — confirmed exactly as the issue describes (a manager/staff repair would silently reassign restaurant ownership). While building a regression test for the legitimate case (the actual owner's account being repaired), also found a second, more severe pre-existing bug in the same code path: the old `public.users` row was deleted *before* `restaurants.owner_id` was updated, but `restaurants_owner_id_fkey` has no `ON DELETE` action — so deleting the current owner's row while `owner_id` still pointed at it would fail outright with a foreign-key violation (400 response). In other words, owner account repair was actually broken today, not just "unexpectedly reassigning" — it was reachable failure, not just a design smell.
**What was done:** (1) Only reassign `restaurants.owner_id` when the relinked row's role is `'owner'` (`payload.role === 'owner'`) — manager/staff repairs now leave ownership untouched. (2) Reordered the relink steps so the old owner row is detached from `restaurants.owner_id` (set to `NULL`, column is nullable) *before* it's deleted, then the new row is inserted, then `owner_id` is reattached to the new id if the role is owner — avoiding both the FK violation and the `users_email_key` unique-constraint conflict that a naive insert-before-delete would hit.
**Verification:** Added `scripts/verify-sync-profile-owner-guard-staging.ts` and ran it for real against staging (`mdqjpxwczrhkxkbqatqa`) by calling the actual route handler directly with real signed-in access tokens: (1) manager account repair (real auth user + real sign-in) — confirmed `restaurants.owner_id` unchanged after relink; (2) owner account repair (regression guard for the legitimate case) — confirmed relink succeeds (previously would have 400'd on the FK violation) and `restaurants.owner_id` correctly updates to the new auth id. Both cases passed. Test data cleaned up after.

## #33 — Investigate AuthProvider remount on Settings navigation
**Outcome:** Investigated — no bug, no fix needed (closed)
**What was found:** The original observation came from `scripts/verify-sign-in-methods-staging.ts`'s check6, which reaches Settings via `page.goto('${BASE_URL}/settings#profile')`. `page.goto()` is always a full browser navigation in Playwright (equivalent to typing the URL and hitting enter, or a hard reload) — that alone tears down and rebuilds the entire page, including the root layout's `AppProviders`/`AuthProvider`, completely independent of which route it lands on. The real (and only) way a signed-in user reaches Settings in the app is clicking the sidebar `<Link href="/settings">` in `components/dashboard/dashboard-sidebar.tsx` — a Next.js client-side transition that keeps the shared root layout (and everything inside it, including `AuthProvider`) mounted across navigation, since `/dashboard` and `/settings` are both under the same `app/(staff)/layout.tsx` route group.
**What was done:** No code change — this was purely an investigation issue. Wrote `scripts/verify-authprovider-remount-staging.ts` to isolate the variable: sign in once (one unavoidable full navigation to bootstrap the session, matching how a real user's first page load works), record the AuthProvider mount count, then perform the *real* navigation path — clicking the sidebar Settings link — and check for any additional mount/unmount console events.
**Verification:** Ran the script for real against staging (`mdqjpxwczrhkxkbqatqa`) with a real seeded owner account and a real Playwright browser session. Result: 1 AuthProvider mount after the initial dashboard load, still 1 mount and 0 unmounts after clicking the sidebar Settings link — no remount occurs on real client-side navigation. Confirms the issue's own hypothesis ("likely a layout or route-group remount... needs its own investigation") resolves to: it isn't a route-group remount at all, it's specific to how the earlier verification script reached the page.
